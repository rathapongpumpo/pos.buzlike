# เฟส 3 — สมาชิกและการชำระเงิน

วันที่ตรวจ: 10 พฤศจิกายน 2026 · โปรเจ็กต์ปัจจุบัน `D:\Projects\1.buzlike\pos.buzlike`

**สถานะ: งานระบบและการทดสอบ local ผ่าน แต่เกณฑ์เชื่อมต่อผู้ให้บริการยังรอ Stripe Sandbox** ผู้ใช้ยืนยันว่ายังไม่มีบัญชี Stripe จึงไม่ได้สร้างบัญชีแทน ไม่ได้ใส่ keys จำลองลง `.env` ไม่ได้เรียกเก็บเงินจริง และยังไม่ถือว่าพร้อม go-live

## สิ่งที่ทำ

- เลือก Starter/Pro รายเดือน/รายปี หรือ Lifetime จากหน้าแรก แล้วคงแพ็กเกจผ่านสมัคร เข้าสู่ระบบ ยืนยันอีเมล ตั้งร้าน และกลับมาใหม่ เก็บความต้องการไว้กับบัญชี ไม่สร้างร้าน/สมาชิก/การชำระจากการโหลดลิงก์ล่วงหน้า
- ลูกค้าที่มีหลายธุรกิจเลือกธุรกิจที่จะซื้อให้ได้ พนักงานทั่วไปซื้อแพ็กเกจแทนเจ้าของไม่ได้ ธุรกิจใหม่เริ่มแคตตาล็อกเปล่าและสิทธิ์ทดลองเดิม จ่ายสำเร็จแล้วเปิดสิทธิ์กับธุรกิจและบัญชีเดิม
- หน้าชำระแสดงราคา VAT 7% ยอดรวม รอบตัดบัตร และความต่างระหว่างบัตรอัตโนมัติ / PromptPay จ่ายเอง / สลิปที่ต้องรอตรวจ ระบบปิดช่องทางที่ยังไม่ตั้งค่า
- ตรวจยอดที่ลูกค้ายืนยันกับราคาจากฐานข้อมูลอีกครั้งก่อนสร้างรายการ คูปองคิดก่อน VAT; สำหรับบัตร recurring ส่วนลดคงอยู่ทุกงวดของสมาชิกนั้น และมีข้อความแจ้งก่อนจ่าย
- บันทึกคำขอและรหัสกันซ้ำก่อนติดต่อ Stripe; retry ใช้รายการและ provider idempotency key เดิม ป้องกันสมาชิกซ้อน รายการค้างที่กำกวมต้องยืนยันกับผู้ให้บริการก่อนเปิดรายการใหม่
- มีปุ่มชำระรายการเดิม ตรวจสถานะ และยกเลิกรายการที่ยังไม่รับเงิน การกลับจากหน้า Checkout หรือแก้ URL ไม่เปิดสิทธิ์ ต้องอ่านยอดรับเงินจาก provider ฝั่ง server
- รับ webhook ด้วย raw body และตรวจลายเซ็น/โหมด เก็บ inbox ถาวรก่อนตอบรับ worker จองงาน ลองใหม่พร้อม backoff และกู้ lease ที่ค้าง
- เปิดสิทธิ์ subscription ตาม `invoice` ที่จ่ายแล้วและรอบจาก Stripe ใช้ invoice ID กันซ้ำ ไม่บวกวันซ้ำจาก event คนละ ID และอ่านสถานะปัจจุบันเพื่อไม่ให้ event เก่าทับสถานะใหม่
- รองรับต่ออายุไม่สำเร็จและ grace 3 วัน ยกเลิกเมื่อจบรอบ เปิดต่ออายุอีกครั้ง และเปลี่ยนบัตรผ่าน hosted portal การยกเลิกคงสิทธิ์ที่จ่ายไว้จนจบรอบ ไม่เปลี่ยนสถานะระงับโดยผู้ดูแลให้กลับมาใช้ได้เอง
- คืนเงินบางส่วนบันทึกยอดโดยไม่ตัดสิทธิ์ทันที คืนเต็มตัดเฉพาะสิทธิ์ของรายการนั้น หรือคืนไปใช้รอบอื่นที่ยังจ่ายไว้ การส่ง event เดิมซ้ำไม่เปิดสิทธิ์ของรายการคืนเงินกลับมา
- worker ตรวจสมาชิก รายการค้าง และรายการ one-off ที่ยังมีสิทธิ์ เพื่อกู้กรณี webhook ไม่มา รวมถึงกรณีสร้าง Checkout สำเร็จแต่ response หายและลูกค้าไม่กลับมากดซ้ำ
- ใบเสร็จเก็บชื่อผู้ซื้อ ที่อยู่ ชื่อแพ็กเกจ และราคาขณะซื้อ การแก้ชื่อร้านหรือข้อมูลบริษัทภายหลังไม่แก้เอกสารเก่า มีประวัติยอดคืนเงิน พิมพ์/บันทึก PDF ผ่าน browser ได้
- UI หน้าสมาชิก ประวัติและเอกสารรองรับมือถือ/แท็บเล็ต ปุ่มจัดการรายการสูงอย่างน้อย 44 px

ราคายังเป็นราคาที่อนุมัติเดิม: Starter 390/3,500 บาท และ Pro 790/7,500 บาท ก่อน VAT; ยอดรวม VAT คือ 417.30/3,745 และ 845.30/8,025 บาทตามลำดับ

## ผลทดสอบ

- `npm test` บน production build ที่รันในเครื่อง: **53 ผ่าน / 0 ไม่ผ่าน** รวมของเดิม 38 และเฟส 3 เพิ่ม 15
- `npm run typecheck` และ `npm run build` ผ่าน
- ทดสอบ billing ด้วย PostgreSQL จริงและ Stripe adapter จำลอง: response หายหลัง provider สร้างรายการ, การกดพร้อมกัน, request เดิมข้อมูลต่างกัน, ยอดผิด, invoice มาก่อน checkout, event ซ้ำ/เก่า, ต่ออายุ, grace, suspension, partial/full refund, ยกเลิกรายการ/async payment ล้มเหลว, กู้รายการโดยไม่ใช้ browser และ subscription ที่ยังไม่จ่ายห้ามข้ามวันหมดทดลอง
- ทดสอบ HTTP จริง: สมัครพร้อมแพ็กเกจ → ลิงก์ยืนยันอีเมล → session ใหม่ → ตั้งร้านเปล่า; ตรวจว่า prefetch ไม่เปลี่ยนความต้องการ; ยืนยันราคา; owner/cashier; ข้ามรายการต่างร้าน; ช่องทางที่ไม่มี keys ตอบปฏิเสธและไม่สร้างรายการการเงิน
- ทดสอบ webhook HTTP handler ด้วยลายเซ็นทดสอบจริงของ SDK และ raw body; แก้เนื้อหาจะไม่ผ่าน รายการซ้ำไม่เพิ่ม inbox
- Playwright แบบ headless บนหน้าจริงจาก local production build: 360×800, 390×844, 768×1024, 1024×768 ความกว้างเอกสารเท่ากับ viewport ทั้งหมด ปุ่มรายการสูงอย่างน้อย 44 px; ตารางเปรียบเทียบเลื่อนภายในได้
- ตรวจภาพ checkout, ข้อมูลบริษัท และใบเสร็จ ไม่มี browser console error ในการตรวจ production build ข้อมูลในภาพเป็น fixture และลบออกหลังตรวจ ไม่ใช่บัญชีลูกค้าหรือหลักฐาน Stripe Sandbox

ภาพหลักฐานอยู่ใน `output/playwright/phase3-*.png` และผลขนาดหน้าจอใน `docs/phases/evidence/phase3-local.json`

## เงื่อนไขและสิ่งที่ยังรอ

1. ยังไม่มีบัญชี Stripe: ยังไม่ยืนยัน hosted Checkout, PromptPay จริง, การตัดบัตรรอบถัดไป, portal, การคืนเงิน และ webhook ผ่านเครือข่าย Sandbox ต้องทดสอบตาม [คู่มือ billing](../billing-operations.md) ก่อนผ่านเกณฑ์ผู้ให้บริการ
2. ต้องมี billing worker และ email worker ที่ดูแลด้วย process supervisor พร้อม alert ใน staging/production เฟส 4; ระหว่าง automated tests ไม่รัน SMTP worker จริงเพื่อไม่ส่งอีเมล fixture ออกไป
3. เปลี่ยนแพ็กเกจของสมาชิกบัตรโดยยกเลิกการต่ออายุแล้วเริ่มแพ็กเกจใหม่หลังสิ้นสุดรอบเดิม **ยังไม่มี prorated upgrade/downgrade กลางรอบ** และไม่สร้าง subscription ซ้อนเพื่อทำเสมือนรองรับ
4. Refund ในเฟสนี้รับสถานะจาก Stripe และปรับบัญชี/สิทธิ์ ไม่ได้มีปุ่มอนุมัติคืนเงินสด/โอน หรือระบบขอคืนเงินอัตโนมัติ ต้องกำหนดนโยบายและสิทธิ์ผู้ดำเนินการก่อนเปิดขาย
5. ใบเสร็จในระบบยังไม่ใช่ e-Tax Invoice ต้องยืนยันข้อมูลนิติบุคคลผู้ขาย การจด VAT และนโยบายเอกสารก่อน production ในเฟส 4
6. Lifetime เปิดสิทธิ์ซื้อขาดและ export ตามระบบเดิม; การจัดเก็บค่าดูแล Cloud ปีถัดไป 1,500 บาทและการส่งมอบระบบติดตั้งเองยังต้องปิดเงื่อนไข/ทดสอบในเฟส 4–5 ก่อนเปิดขาย Lifetime จริง
7. Reconcile ปกติเก็บ webhook ที่ตกหล่นย้อนหลัง 1 ชั่วโมงและตรวจข้อมูลสมาชิกปัจจุบัน; `--all` กู้ event ย้อนหลัง 29 วันและขยายจำนวนธุรกิจ/รายการที่ตรวจ แต่ไม่ได้เป็นการตรวจสอบบัญชีประวัติ Stripe ทั้งบัญชีตลอดอายุ ต้องตรวจและแจ้งเตือน worker หยุดนานในเฟส 4

เฟสถัดไปคือเฟส 4: production configuration, worker supervision/alerts, backup restore/rollback และนโยบายการขาย โดยยังมี Stripe Sandbox เป็น dependency ค้างของเฟส 3
