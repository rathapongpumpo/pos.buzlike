# Pilot A — ฐานข้อมูลและกติกาสิทธิ์

สถานะ: **ผ่านการตรวจใน local** · 11 พฤศจิกายน 2026 · โปรเจ็กต์ `D:\Projects\1.buzlike\pos.buzlike`

ทำฐานสำหรับนำร่อง 5 ธุรกิจ ใช้ Pro ฟรี 30 วัน โดยยังไม่เปิดรับร้านจริง หน้าเว็บและเส้นทางคำเชิญสำหรับลูกค้าอยู่ในเฟส B ไม่มีการ deploy production หรือทดสอบเรียกเก็บเงินจริงในเฟสนี้

## สิ่งที่เปลี่ยน

- เพิ่ม migration `20261110161000_pilot_foundation`: release settings, campaign, invitation, enrollment, waitlist, feedback/history และ audit พร้อมความสัมพันธ์กับเจ้าของ ธุรกิจ สาขา พนักงาน และ email outbox
- ใช้ foreign key แบบประกอบป้องกันการผูกสิทธิ์/ฟีดแบ็กข้ามธุรกิจ กำหนด unique/check constraints และ trigger ป้องกันการเปลี่ยนเจ้าของ ย้ายร้าน ลบ grant ที่เริ่มใช้แล้ว หรือรับสิทธิ์เกินโควตา
- จองได้หลังยืนยันอีเมลตรงคำเชิญเท่านั้น เก็บ hash ของ token; คำเชิญอายุ 7 วัน การจองไม่เกิน 72 ชั่วโมงและไม่เกินอายุคำเชิญ หนึ่งเจ้าของได้หนึ่งธุรกิจต่อโครงการ
- ล็อกและนับโควตาใน transaction: การจองหมดอายุก่อนเริ่มคืนที่ว่างได้ แต่สิทธิ์ที่เริ่มแล้วนับเป็นสิทธิ์ที่ใช้ไปตลอด ไม่แจกวนเกิน 5 ธุรกิจ
- เปิดร้านเปล่าและ activate ใน transaction เดียว เริ่ม 30 × 24 ชั่วโมงเพียงครั้งเดียว การส่งซ้ำได้ร้านและวันสิ้นสุดเดิม ถ้าขั้นตอนใดล้มเหลว rollback ทั้งชุด
- เพิ่ม `PILOT_PRO_V1`: สูงสุด 3 สาขา; ไม่จำกัดสินค้า พนักงาน และเครื่องขาย; เปิด KDS, QR, BOM และ export โดยแยก grant จากแพ็กเกจที่ชำระเงินจริง ไม่แก้ `isLifetime` หรือสร้างใบเรียกเก็บเงินปลอม
- รวมการอ่านสิทธิ์ที่ license guard, bootstrap, billing status, quota สาขา/เครื่อง/สินค้า/ทีม, ขาย, BOM และ public QR; ใช้เวลาฐานข้อมูลตัดสิทธิ์เมื่อครบกำหนด แม้ worker ไม่ทำงาน ไม่ย้อนกลับไปให้ trial 14 วัน
- คงคำสั่งระงับ/อ่านอย่างเดียวและสิทธิ์สมาชิกชำระเงินเดิม เจ้าของร้านนำร่องที่หมดสิทธิ์ยังอ่าน/ส่งออกรายงานได้
- เพิ่ม release policy: เมื่อเป็น `PRIVATE_PILOT` จะปิด checkout ใหม่ทุกวิธี รวมการ resume checkout และปิด onboarding ที่ไม่มีการจอง; งานสถานะ/เว็บฮุกของรายการเดิมยังทำงานได้
- เพิ่ม client guard สำหรับวันหมดสิทธิ์ที่ cache ไว้ บิลเงินสดที่ server ปฏิเสธยังอยู่ในคิวให้ตรวจสอบ ลบเมื่อได้รับผลสำเร็จเท่านั้น
- แก้ transaction retry ให้รองรับ PostgreSQL serialization/deadlock ที่ Prisma ส่งผ่าน `P2010` เพื่อให้คำขอพร้อมกันไม่จบด้วยข้อผิดพลาดภายใน

## งานที่ยังไม่อยู่ในเฟส A

- **B:** public invite/context/claim, รักษาคำเชิญข้ามสมัคร/ยืนยันอีเมล, waitlist, หน้าเว็บและสมาชิก พร้อมตรวจ mobile/tablet ด้วย browser และภาพจริง
- **C:** UI ผู้ดูแล/ฟีดแบ็ก, ส่ง/หมุน/ถอนคำเชิญ, reminder/expiry workers; ตารางและบริการแกนบางส่วนมีแล้ว แต่ยังไม่มี flow เหล่านี้ครบให้ผู้ใช้ใช้เอง
- **D:** staging/production, supervisor/alerts, ซ้อม restore backup และอุปกรณ์จริง ยังไม่ได้ทดสอบใน A
- Offline ทดสอบ queue ด้วย Dexie stub และ guard ระดับโค้ด ยังไม่ใช่หลักฐาน IndexedDB/ตัดเครือข่ายบนมือถือหรือ tablet จริง
- ยังไม่ส่งอีเมลนำร่องจริง ไม่เปิด pilot และไม่ทดสอบ Stripe provider; Stripe เป็นงานเฟส F ก่อนเปิดรับเงิน

ผลส่งมอบเฟส A พร้อมให้ทำเฟส B ต่อ โดยยังต้องผ่าน B–D ก่อนออกคำเชิญให้ร้านจริง
